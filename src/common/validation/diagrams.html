Validation Module — Visual Reference

Two views of src/common/validation/, each answering a different question.

  1. State Diagram — what the data becomes
  2. Flowchart — what runs, and where it branches

1. State Diagram

The lifecycle of a single payload — every state it can occupy, and what moves it on.

stateDiagram-v2
    [*] --> RawInput : request arrives

    RawInput --> Validating : pipe.transform(value)

    Validating --> Parsed : safeParse succeeded
    Validating --> Rejected : safeParse failed

    Parsed --> Trusted : returned to controller
    Trusted --> [*] : 201 Created

    Rejected --> DomainError : throw ValidationFailedError
    DomainError --> HttpError : exceptionFactory.create()
    HttpError --> ErrorEnvelope : HttpExceptionFilter
    ErrorEnvelope --> [*] : 400 or 422

    note right of Parsed
        Data may have CHANGED here:
        transform(Number) etc.
    end note

    note right of DomainError
        Still framework-free.
        No HTTP knowledge yet.
    end note

How to read this drawing

Rounded boxA state — a condition the data rests in.
ArrowA transition — moving from one state to the next.
Arrow labelThe trigger that causes the transition.
● filled circleStart and end of the lifecycle.
NoteA fact about that state, not a step.

What the shape is telling you

  • There is no arrow back into Validating. Once data leaves that state it is never re-checked. Nothing downstream re-validates, which is exactly why the controller can trust what it receives — and also why a bug in the schema cannot be caught later.
  • Parsed and RawInput are not the same data. The note marks where transform(Number) and friends run. A payload that entered as "12345678901234" (string) leaves as a number. The state diagram makes that mutation an explicit state change rather than a hidden side effect.
  • The failure path has three distinct states, not one. DomainError → HttpError → ErrorEnvelope. Each is owned by a different class, and each knows less about HTTP than the next. Collapsing them into one state would be the same as hard-coding the response format inside the validator.
  • Both terminal arrows lead to the same [*]. Every request ends — there is no state the data can get stuck in, and no path that silently drops it.

2. Flowchart — Request Lifecycle

One request, from arrival to response, through both possible outcomes.

flowchart TD
    A["HTTP Request — POST /customer"] --> B["NestJS matches route"]
    B --> C["SchemaValidationPipe.transform"]
    C --> D["validator.validate"]
    D --> E["schema.safeParse"]
    E --> F{"success?"}

    F -->|yes| G["return parsed data"]
    G --> H["Controller method runs"]
    H --> I["CustomerService.createCustomer"]
    I --> J["HTTP 201 Created"]

How to read this drawing

RectangleA step that runs.
Diamond (amber)A decision — the path splits here.
Arrow labelThe condition under which that branch is taken.
Green endSuccess exit.
Red endFailure exit.
Top to bottomTime. Steps happen in the order drawn.

What the shape is telling you

  • Exactly two exits, and they never merge. Either the controller runs and you get 201, or you get a structured JSON error. The controller body is never reached with invalid data — which is why controller code can trust its input and skip defensive checks.
  • The two diamonds are different kinds of question. The first (success?) is answered at runtime, from the data in the request. The second (which factory?) was already answered at startup, when zodBody() or zodQuery() built the pipe. Nothing inspects the request to pick a status code — the choice is baked into which preset the route used. That is the Strategy pattern visible as a branch that was decided before the request even arrived.
  • The mapping box is where library coupling ends. map ZodIssue to ValidationIssue is the last point where Zod-specific shapes exist. Every box after it works with our own types. Swap Zod for Joi and only this one box changes; everything downstream is untouched.
  • Two translation layers, not one. The pipe turns a domain error into an HTTP error; the global filter turns that into the final response envelope. Keeping them separate is why validation code never hard-codes the response format.

How the two diagrams fit together

Same request, two questions. Each drawing is silent about what the other explains.

DiagramAnswersCannot showReach for it when…
State What does the data become? Who performs each transition. You are asking whether data was mutated, or where it can get stuck.
Flowchart What runs, in what order, and where does it branch? That the data itself changed along the way. You are debugging one specific request.

Where they disagree — and why that is useful

  • The flowchart shows return parsed data as a single quiet box. The state diagram insists it is a genuine change of state, with a note attached. Same line of code, two levels of alarm — and the state diagram is the one telling the truth: a nationalID that arrived as the string "123456789012345" leaves as a number.
  • The flowchart's failure path looks like plumbing. Boxes flow from throw to exceptionFactory.create to HttpExceptionFilter as if they were routine steps. The state diagram reframes exactly those steps as three distinct states — DomainError, HttpError, ErrorEnvelope — each knowing less about HTTP than the next. What looks like plumbing is actually the module's central design decision.
  • The flowchart can show a dead end; the state diagram cannot hide one. Because every state must lead somewhere, the state diagram is the faster way to confirm no request gets stuck. Both terminal arrows reach [*], so every request ends.
